Audit notes

  • 11 findings. The service has no OpenTelemetry code at all: no SDK, no provider, no exporter, no instrumentation package in go.mod.
  • Highest priority is the SDK bootstrap plus HTTP server spans named by chi route pattern and database/sql client spans; together they make per-request query fan-out (N+1) visible in a trace waterfall.
  • Every hot handler issues queries in loops (nearby-chairs, notification chair stats, ride history, owner sales), and the schema has no secondary indexes, so DB spans are the main diagnostic signal for this service.
  • The outbound payment gateway call retries up to 5 times with 100ms sleeps inside an open DB transaction; it needs client spans and retry visibility.
  • No route-aware chi instrumentation exists in opentelemetry-go-contrib; route names must come from chi's RoutePattern applied onto otelhttp spans.
  • The internal matching endpoint (polled every 0.5s) and slog error logging are recommended follow-ups once the baseline is in place.
